# 第 6 章　測試策略：怎麼知道自己是對的

> **本章目標**
> 1. 理解數值程式測試的核心難題——**測試預言（test oracle）**：正確答案從哪裡來？
> 2. 學會六種取得正確答案的方法，並知道各自能抓到、抓不到什麼錯誤
> 3. 學會寫**性質測試**與**蛻變測試**，以及如何讓隨機測試可重現
> 4. 學會測試時間、並行、效能與架構這些「難測」的東西

---

## 6.1 數值程式的特殊難題

一般的商業程式，正確答案通常可以手算或從規格直接讀出：「訂單總額 = 單價 × 數量」。
但對 SGP4 來說，「ISS 在 2026-10-21 10:50:00 UTC 的位置是多少公里？」——**沒有人知道正確答案**，除非用另一個程式算。

這就是**測試預言問題**：要判斷輸出是否正確，你需要一個「預言」（oracle）告訴你正確答案，或至少告訴你「錯了」。
本專案用了六種預言，各有不同的強項：

| 預言 | 正確答案的來源 | 能抓到的錯誤 | 抓不到的錯誤 | 本專案的例子 |
|---|---|---|---|---|
| ① 已發表的參考值 | 權威文獻 | 實作錯誤 | 文獻沒涵蓋的情況 | Vallado 的 `tcppver.out` |
| ② 參考實作產生的資料 | 另一個公認正確的程式 | 移植錯誤 | 兩者共同的錯誤（理解錯公式） | python-sgp4 產生的 320 組隨機軌道 |
| ③ 高精度獨立計算 | 同一公式、更高精度 | 精度不足 | 公式本身錯 | GMST 用 60 位十進位計算 |
| ④ 獨立的參考演算法 | 完全不同的演算法解同一個問題 | 演算法遺漏、邊界錯誤 | 兩者共用部分的錯誤 | 逐秒暴力過境搜尋 |
| ⑤ 性質與不變量 | 「無論輸入是什麼都必須成立」的關係 | 違反結構的錯誤 | 「結構正確但數值錯」 | 視窗拆分不變、遮罩單調性 |
| ⑥ 手算範例 | 人逐步推導 | 公式理解錯誤（人工審核） | 規模大的錯誤 | 50 組逐步手算範例 |

> **教學重點**：沒有一種預言是萬能的。好的測試策略是**組合**多種預言，讓它們的盲點互相覆蓋。
> 例如：② 抓不到「我和 Python 都把公式理解錯」，但 ① 和 ⑥ 可以；④ 抓不到「SGP4 本身錯」，但 ② 可以。

## 6.2 參考資料：可重現、可追溯

所有參考資料都由 `tools/refgen/` 的 Python 腳本**離線**產生並提交進 repo。三個原則：

1. **固定版本**：`requirements.txt` 固定 `sgp4==2.27`；腳本會檢查 `sgp4.api.accelerated == True`，確保用的是 Vallado 官方 C++ 程式碼，而不是純 Python 的版本
2. **固定亂數種子**：重新執行會得到逐位元相同的檔案
3. **完整精度**：以 Python 的 `repr` 輸出（17 位有效數字），不會因為列印而損失精度

一個反例值得記住：Vallado 發表的 `tcppver.out` 速度只印到小數 9 位，**不夠**驗證 1e-9 km/s 的門檻（列印本身就有 5e-10 的捨入誤差）。
所以我們改用 python-sgp4 以完整精度重新產生，另外再拿 `tcppver.out` 在它的列印精度內交叉比對。

### 獨立性：參考值不能「抄」被測程式

座標轉換的參考值是用 Python 依需求的公式**重寫一次**算出來的，不呼叫 C# 程式。這能抓到「C# 寫錯了」，但**抓不到「公式本身錯了」**——這是 ② 類預言的盲點，測試報告中誠實地列為已知風險。

## 6.3 獨立的參考演算法：暴力過境搜尋

過境搜尋是最複雜也最容易出錯的演算法。它的預言是一個**刻意寫得笨但一定對**的版本：

```csharp
// tests/SkyPass.Tests/Reference/BruteForcePassFinder.cs（設計說明）
/// 刻意與正式程式碼的 SkyPass.Core.Passes 互相獨立：只共用傳播與座標轉換（Observation），
/// 演算法則完全不同——從視窗起點逐秒取樣仰角，以二分法細化 AOS/LOS，以黃金分割法細化最大仰角。
/// 不使用仰角變化率，也不依賴任何取樣格點對齊。
```

設計參考演算法的規則：

| 規則 | 理由 |
|---|---|
| **不共用被測演算法的任何程式碼** | 共用的部分有 bug，兩邊會一起錯，測試照樣通過 |
| **用最簡單、最不可能錯的方法** | 逐秒取樣 30 倍慢，但「不漏」幾乎不需要證明 |
| **可以慢** | 它只在測試中跑 |
| **明確列出共用了什麼** | 這裡共用了 SGP4 與座標轉換——所以它們必須由其他預言（①②③）另外驗證 |

比對時，邊界過境（最大仰角與遮罩差 < 0.05°）兩邊都可能有、也可能沒有，需求允許容忍：

```csharp
// 最大仰角與遮罩相差 < 0.05° 的邊界過境，兩邊是否納入都可接受
var exp = expected.Where(p => p.MaxElevationDeg - sc.MaskDeg >= BorderlineDeg).ToList();
// …每個「明確的」參考過境都必須在正式結果中找到，且 AOS/LOS ≤ 0.1 秒、最大仰角 ≤ 0.01°
// …每個正式結果中「明確的」過境，也必須在參考解中有對應（不能多）
```

注意比對是**雙向**的：不能漏（參考有、正式沒有），也不能多（正式有、參考沒有）。

## 6.4 性質測試：讓電腦想測試案例

手寫的測試案例只能涵蓋你想得到的情況。**性質測試**讓電腦隨機產生大量輸入，檢查某個性質對每一個都成立。

本專案沒有引入 FsCheck 之類的套件，而是寫了一個 30 行的小工具：

```csharp
// tests/SkyPass.Tests/Support/Property.cs
public static void Run(string name, int seed, int iterations, Action<Random> check)
{
    for (var i = 0; i < iterations; i++)
    {
        var caseSeed = CaseSeed(seed, i);
        try
        {
            check(new Random(caseSeed));
        }
        catch (Exception ex)
        {
            throw new PropertyFailedException(
                $"性質 '{name}' 在第 {i} 次失敗。重現：Property.Replay(caseSeed: {caseSeed})（seed={seed}）。原因：{ex.Message}", ex);
        }
    }
}
```

兩個關鍵設計：

1. **固定種子**：每次執行都產生相同的案例，CI 不會時好時壞
2. **每個案例有自己的衍生種子**：失敗時訊息直接告訴你 `caseSeed`，用 `Property.Replay(caseSeed, …)` 就能**單獨重跑那一個案例**來除錯，不必跑完前面幾百個

一個典型的性質測試：

```csharp
// tests/SkyPass.Tests/Core/Tle/TleFormatterTests.cs
Property.Run("TLE 往返（格式化→解析→格式化）", seed: 7102, iterations: 3000, rng =>
{
    var original = RandomTle(rng);                       // 在 TLE 能表達的離散格點上隨機產生
    var (l1, l2) = TleFormatter.FormatLines(original);
    var parsed = TleParser.Parse($"{original.Name}\n{l1}\n{l2}");

    Assert.Empty(parsed.Errors);
    Assert.Equal(original with { Line1 = l1, Line2 = l2 }, Assert.Single(parsed.Sets));
});
```

> **教學重點**：隨機產生輸入時要注意「輸入空間」。TLE 的傾角只有 4 位小數，如果隨機產生 `51.64163829…`，
> 格式化後一定會失真，測試就會因為**錯誤的期望**而失敗。`RandomTle` 只在格式能精確表達的格點上取值。

## 6.5 蛻變測試：不知道答案，也能測

有些情況連參考實作都沒有。**蛻變測試**（metamorphic testing）的想法是：
我不知道 f(x) 的正確答案，但我知道 f(x) 與 f(x′) 之間**應該有什麼關係**。

| 蛻變關係 | 輸入的變化 | 輸出應有的關係 |
|---|---|---|
| 視窗拆分不變性 | [t₀, t₂] → [t₀, t₁] + [t₁, t₂] | 合併後與一次預測相同 |
| 遮罩單調性 | 遮罩 m → m′ > m | 高遮罩的每個過境都包含在某個低遮罩的過境中 |
| 執行緒數無關 | 1 個執行緒 → N 個執行緒 | 逐位元相同 |
| TLE 往返 | 解析 → 格式化 → 解析 | 欄位不變 |
| 座標往返 | 大地 → 地固 → 大地 | 回到原點（≤ 1e-9） |

這些測試的威力在於：**它們不需要知道任何正確答案**，卻能抓到很多真實的 bug。
例如視窗拆分不變性，在開發初期如果取樣格點不是全域對齊（第 4 章），這個測試就會失敗。

## 6.6 攻擊弱點：構造刁鑽的案例

隨機測試很少碰到最危險的情況。對每個演算法，先問「它最可能在哪裡失敗？」，然後**刻意構造**那種情況。

### 案例一：掠過過境

演算法的弱點是「極值剛好略高於遮罩」。構造方法：

```csharp
// tests/SkyPass.Tests/Core/Passes/PassFinderPropertyTests.cs（概念）
// 1. 用暴力參考解找出某個過境的最大仰角 E
// 2. 把遮罩設成 E − δ，其中 δ ∈ [0.05°, 0.5°]
// 3. 要求正式演算法一定要找到這個過境
var delta = 0.05 + rng.NextDouble() * 0.45;
return (sc with { MaskDeg = target.MaxElevationDeg - delta }, target);
```

這比「隨機取遮罩，希望碰到掠過的情況」有效得多：60 個案例全部都是最難的那種。

### 案例二：擦邊短陰影

陰影搜尋的弱點是「陰影比取樣間隔短」。真實資料中很少見，所以用**幾何**構造：

```
圓軌道的陰影深度由 β 角（軌道面與太陽方向的夾角）決定
→ 掃描升交點赤經，找到「有陰影 → 沒陰影」的臨界值
→ 二分法逼近到陰影深度恰為 0.0002 km、0.001 km、0.005 km、0.015 km
→ 對應約 1、2、5、8 秒的陰影
```

先用 0.05 秒的暴力取樣**確認情境真的成立**（最短陰影 < 10 秒），再要求 10 秒步長的搜尋找到它。
「先驗證測試情境本身」這一步很重要——第一次寫這個測試時，我們估計的深度太大，構造出來的陰影有 37 秒，
如果沒有這個檢查，測試會「通過」但其實什麼都沒測到。

> **教學重點**：測試也會有 bug。**斷言你的測試情境確實是你以為的那個情境**（例如「這個陰影真的短於 10 秒」），
> 否則測試可能在錯誤的理由下通過。

## 6.7 測試時間

所有「現在」都透過注入的 `TimeProvider`，測試用 `FakeTimeProvider`（自己寫的，20 行）：

```csharp
public sealed class FakeTimeProvider(DateTimeOffset now) : TimeProvider
{
    private DateTimeOffset _now = now;
    public override DateTimeOffset GetUtcNow() => _now;
    public void SetUtcNow(DateTime utc) => _now = /* … */;
    public void Advance(TimeSpan delta) => _now += delta;
}
```

這讓需求中的「時間回溯後狀態正確」「倒數每秒減少 1 秒」「陳舊（超過 14 天）」都能精確測試：

```csharp
clock.Advance(TimeSpan.FromDays(-1));      // 時間回溯一天
p.Tick();
await p.WhenIdleAsync();                   // 等背景重建過境快取
var reading = p.Tick()!;
Assert.True(reading.NextPass!.Aos.SecondsSince(first.Aos) < -3600);
```

## 6.8 測試並行與取消

並行的 bug 通常很難重現。本專案用三種方式測試：

| 性質 | 測試方式 |
|---|---|
| 結果與執行緒數無關 | 同一個請求以 1 個與 N 個執行緒各算一次，**逐欄位、逐位元**比較（`double` 用 `==`，不用容差） |
| 取消不留半套結果 | 在進度回報到第 3 顆衛星時取消，斷言方法擲出 `OperationCanceledException` 且結果變數**從未被賦值** |
| 進度單調遞增 | 用**同步**的進度接收器（`SynchronousProgress`）記錄每一次回報，檢查嚴格遞增 |

最後一點有個陷阱：.NET 內建的 `Progress<T>` 會把回報**非同步地**排到執行緒池，順序不保證。
如果用它來測「進度單調遞增」，測試本身就會不穩定。所以測試用了一個在呼叫端同步執行的接收器。

## 6.9 效能測試

效能測試是最容易「不穩定」的測試。本專案的做法：

| 做法 | 理由 |
|---|---|
| 放在**不平行**的測試集合（`DisableParallelization = true`） | 開發中發現：與其他測試平行時，即時追蹤曾出現 1.2 ms 的離群值；隔離後最大值降到約 50 µs |
| 先**暖機**再量測 | 第一次呼叫包含 JIT 編譯時間 |
| 用**百分位數**斷言（P99.9 ≤ 1 ms），並輸出中位數、最大值 | 單次最大值受作業系統排程影響，不適合當斷言 |
| 依**核心數**調整預算，並輸出實測值 | 驗收門檻以 8 核心為準，CI runner 核心較少 |

### 測量記憶體配置

「SGP4 熱路徑零配置」用 `GC.GetAllocatedBytesForCurrentThread()` 斷言。開發中遇到兩個教訓：

1. **量測程式本身的配置**：有一次測試在取得「之前」的計數後才 `new Stopwatch()`，結果量到 40 bytes——是 `Stopwatch` 物件本身。修正：先建立量測工具，再取計數
2. **執行環境的一次性配置**：偶爾會量到非零值、之後無法重現。改為**量測三輪取最小值**——一次性的配置只會出現在某一輪；如果熱路徑真的每次呼叫都配置，三輪都會是 10000 × N bytes，照樣失敗

```csharp
// tests/SkyPass.Tests/Support/Allocations.cs
/// 執行環境偶發的一次性配置（例如 JIT 分層編譯）只會出現在某一輪；
/// 熱路徑若每次呼叫都配置，每一輪都會是非零，仍會被測出。
public static long MinimumAllocatedBytes(Action body, int rounds = 3)
```

> **教學重點**：讓測試穩定的方法，絕不能是「讓它比較容易通過」。三輪取最小值之所以合理，
> 是因為我們能**說清楚它排除了什麼、保留了什麼**：排除一次性雜訊，保留真正的退化。

## 6.10 架構測試與規範測試

有些規則不是「功能」，但違反了一樣是缺陷。把它們寫成測試：

```csharp
// tests/SkyPass.Tests/Architecture/LayeringTests.cs（節錄）
// 規格：所有「現在時間」都必須透過 TimeProvider
var pattern = new Regex(@"DateTime(Offset)?\.(Now|UtcNow|Today)\b|Stopwatch\.");
var offenders = Directory.EnumerateFiles(Path.Combine(root.FullName, "src"), "*.cs", SearchOption.AllDirectories)
    /* … */
    .Where(x => pattern.IsMatch(x.line))
    .ToList();
Assert.Empty(offenders);
```

這個測試是在開發最後的「驗收檢查」才加的——加上去的當下就失敗了，抓到兩處違規（第 7 章）。這說明了：
**只寫在文件裡的規則，一定會被違反**。

## 6.12 本章小結

- 數值程式的核心難題是**測試預言**；組合多種預言，讓盲點互相覆蓋
- 參考資料要**固定版本、固定種子、完整精度**，並誠實記錄它的獨立性限制
- 獨立的參考演算法要**刻意不同、刻意簡單**，並明確列出共用了什麼
- 性質測試要**可重現**：固定種子 + 每個案例的衍生種子
- **蛻變測試**在不知道答案時也能抓到 bug
- 針對演算法的弱點**刻意構造**案例，並**斷言情境本身成立**
- 時間、並行、效能、架構都可以測試，前提是設計時就讓它們**可注入、可隔離**

2. **（6-2）蛻變關係**：為都卜勒計算想出兩個蛻變關係（提示：頻率加倍、時間反轉）。
3. **（6-3）找出盲點**：如果需求中的 GMST 公式本身印錯了一個係數，本專案的哪些測試會失敗？哪些不會？為什麼？
4. **（6-4）讓測試失敗**：在 `PassFinder.ProcessInterval` 中刪掉「兩端都在遮罩下、中間短暫升起」那個分支，執行測試。哪些測試失敗？失敗訊息能讓你直接定位問題嗎？
5. **（6-5）重現失敗**：故意讓 `Property_window_split_invariance` 失敗（例如把全域格點改成「從起點開始」），從失敗訊息取得 `caseSeed`，用 `Property.Replay` 單獨重現它。
