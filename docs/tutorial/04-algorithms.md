## 4.1 數值精度：先算一下夠不夠

### 問題

時間在天文計算中通常用**儒略日**（Julian Date, JD）表示：從西元前 4713 年起算的天數。2026 年的 JD 約為 2,461,000。

C# 的 `double` 有 53 位元的有效數字，約 15–16 位十進位。當數值約為 2.46 × 10⁶ 時，相鄰兩個 double 的間距是：

```
2.46e6 × 2⁻⁵² ≈ 5.5e-10 天 ≈ 47 微秒
```

47 微秒看起來很小。但需求要求 GMST（地球自轉角度）誤差 ≤ 1e-9 弧度，而地球每秒轉 7.29e-5 弧度：

```
47e-6 秒 × 7.29e-5 rad/s ≈ 3.4e-9 rad    > 1e-9 rad ✗
```

**單一 double 表示的儒略日，光是「把時間存進去」就已經超過誤差上限。**

### 解法：換一種表示法

把儒略日拆成兩個 double：「當日 0 時的儒略日」（整數 + 0.5）與「日內比例」（0 到 1）：

```csharp
// src/SkyPass.Core/Time/JulianDate.cs（節錄）
/// 兩段式儒略日（UTC）：Day 為當日 0h 的儒略日（整數 + 0.5），Fraction 為日內比例 [0, 1)。
/// 單一 double 的儒略日解析度約 40 微秒，會讓 GMST 誤差超過 1e-9 rad，因此拆成兩段保存。
public readonly record struct JulianDate
{
    public double Day { get; }
    public double Fraction { get; }

    public double MinutesSince(in JulianDate epoch) => ((Day - epoch.Day) + (Fraction - epoch.Fraction)) * 1440.0;
}
```

`Fraction` 在 0 到 1 之間，解析度約 1e-16 天 ≈ 10 奈秒，綽綽有餘。注意 `MinutesSince` 的寫法：**先把整數部分相減、小數部分相減，再相加**——兩個大數相減是精確的，小數相減也是精確的，避免了「大數加小數」的精度損失。

這不是我們發明的：Vallado 的參考實作與 python-sgp4 也是用 `jd, fr` 兩個參數傳遞時間。

> **教學重點**：遇到精度問題，第一個想法常是「換成 decimal 或高精度型別」。
> 但更好的做法往往是**重新選擇表示法**，讓需要精度的部分落在 double 精度最高的範圍（接近 0 的數）。
> 先**估算**誤差（上面那兩行算式），再決定要不要處理——這是數值程式設計的基本功。

### 日期換算：用整數演算法

格里曆轉儒略日的公式有很多版本，常見的「簡化版」只適用 1900–2100 年，在 2100 年（非閏年）會算錯。
本專案用 Fliegel–Van Flandern 的**純整數**演算法，沒有浮點誤差，也正確處理世紀年：

```csharp
private static double FromCalendarDay(long y, long m, long d)
{
    var a = (m - 14) / 12;
    var jdn = (1461 * (y + 4800 + a)) / 4
              + (367 * (m - 2 - 12 * a)) / 12
              - (3 * ((y + 4900 + a) / 100)) / 4
              + d - 32075;
    return jdn - 0.5;
}
```

測試特別涵蓋了 2000-02-29（閏年，因為能被 400 整除）、2100-02-28 → 2100-03-01（非閏年）。

## 4.2 TLE 解析：固定欄位與校驗碼

TLE 是 1960 年代為打孔卡設計的格式：每行 69 字元，每個欄位在固定的欄位置。

```
ISS (ZARYA)
1 25544U 98067A   08264.51782528 -.00002182  00000-0 -11606-4 0  2927
2 25544  51.6416 247.4627 0006703 130.5360 325.0288 15.72125391563537
```

幾個「當年為了省空間」的編碼規則：

| 欄位 | 原文 | 意義 | 規則 |
|---|---|---|---|
| 偏心率 | `0006703` | 0.0006703 | 小數點隱含在最前面 |
| BSTAR | `-11606-4` | −0.11606 × 10⁻⁴ | 符號、5 位尾數（隱含小數點）、指數 |
| epoch 年 | `08` | 2008 | 57–99 → 19xx，00–56 → 20xx |
| 校驗碼 | 最後一位 `7` | 前 68 字元數字和 mod 10 | **負號算 1**，其他非數字算 0 |

### 驗證策略：逐組驗證、精準回報

一個檔案可能有上百組 TLE，其中一組壞掉不應該讓整個匯入失敗。解析器的結構：

1. 把檔案分成「名稱行」與「資料行」，資料行兩兩配對成一組
2. 每一組依序檢查：長度 → 行號 → 校驗碼 → 各欄位格式 → 數值範圍 → 兩行編號一致
3. 錯誤記錄**檔案中的實際行號**與原因，然後跳過該組

```csharp
// src/SkyPass.Core/Tle/TleParser.cs（節錄）
public static int ComputeChecksum(ReadOnlySpan<char> line)
{
    var sum = 0;
    foreach (var c in line[..Math.Min(68, line.Length)])
    {
        if (char.IsAsciiDigit(c)) sum += c - '0';
        else if (c == '-') sum += 1;
    }
    return sum % 10;
}
```

### 一個不明顯的細節：運算順序

BSTAR 的值要怎麼算？`-11606-4` 可以算成 `-0.11606 * Math.Pow(10, -4)`，也可以算成 `-11606 * 1e-9`。
數學上相等，但**浮點結果可能差一個 ULP**。這一點點差異經過 SGP4 傳播一週後，可能放大到超過 1e-6 km 的驗收門檻。

所以解析器刻意採用**與 Vallado 參考實作完全相同的運算順序**：先把尾數解析成 `0.11606`，再乘 `10^指數`。
這是本章反覆出現的主題：**當驗收標準是「與參考實作一致到 1e-6」時，你必須連運算順序都一致。**

### Alpha-5

NORAD 編號即將超過 5 位數。Space-Track 的 Alpha-5 規則：首字元 A–Z（**跳過 I 與 O**，避免和 1、0 混淆）代表 10–33，後接 4 位數字。`E8493` = 14 × 10000 + 8493 = 148493，上限 `Z9999` = 339999。

## 4.3 SGP4：忠實移植，刻意不重構

### 為什麼不重寫？

SGP4 是約 500 行的密集數學，包含大量經驗常數與修正項。需求要求自行實作，且與參考實作的誤差 ≤ 1e-6 km。
要達到這個精度，有兩條路：

| 做法 | 優點 | 風險 |
|---|---|---|
| 讀論文、理解公式、用自己的風格重寫 | 程式碼漂亮、好讀 | 任何一個運算式的順序、括號、常數的寫法不同，都可能讓結果差到超過門檻；而且很難知道錯在哪 |
| **逐行移植參考實作**，保留變數名稱與運算順序 | 可以逐行對照；一旦有差異，二分法就能定位 | 程式碼風格像 C，可讀性較低 |

我們選第二條。`Sgp4Propagator.cs` 的變數名稱（`xmdf`、`argpdf`、`tempa`…）都保留 Vallado 原碼的命名，讓讀者可以並排比對。

> **教學重點**：「重構」不永遠是好事。當程式碼的正確性來自**與另一份程式碼的一致性**時，
> 保持結構相同比「看起來整潔」更重要。這是一個需要判斷的取捨，應該記錄在 ADR 裡。

### 唯一的結構改動：讓它不可變

Vallado 的 `sgp4()` 函數在每次傳播時會**寫回** `satrec` 結構的欄位（`am`、`em`、`nm`…）。在單執行緒的 C 程式裡沒問題，但在平行預報中，多個執行緒同時傳播同一顆衛星就會互相覆蓋。

移植時把這些欄位全部改成**區域變數**：

```csharp
// src/SkyPass.Core/Propagation/Sgp4Propagator.cs（節錄）
/// 與原碼的差異：原碼在 sgp4() 中會寫回 satrec 的平均元素（am、em、nm…），此處全部改為區域變數，
/// 初始化後物件不可變，因此 Propagate 執行緒安全且不配置記憶體。
public sealed class Sgp4Propagator
{
    private readonly double _bstar, _ecco, _argpo, _inclo, _mo, _nodeo, _noUnkozai;
    // …其餘初始化後固定的係數，全部 readonly

    /// 傳播到 epoch 後 tsinceMinutes 分鐘。熱路徑：不配置記憶體、不擲例外、執行緒安全。
    /// 失敗時回傳錯誤碼，state 為 default。
    public Sgp4Error Propagate(double tsinceMinutes, out TemeState state)
```

三個設計約束都在這個簽名上：

- **不擲例外**：失敗時回傳錯誤碼（`Decayed`、`MeanEccentricity`…）。衛星衰減是正常的業務情況，不是程式錯誤
- **不配置記憶體**：輸出用 `out` 參數與 `readonly struct`（`TemeState`、`Vector3d`），預報時這個函數會被呼叫數百萬次
- **執行緒安全**：所有欄位 `readonly`

## 4.4 座標轉換

從 SGP4 的輸出到「方位角、仰角」需要三步：

```
TEME（慣性座標）──[繞 z 軸旋轉 GMST]──► ECEF（地固座標）──[減去觀測點、投影到當地]──► 方位角、仰角、距離
```

### 第一步：TEME → ECEF

地球自轉角 θ = GMST。位置只是繞 z 軸旋轉；速度則多一項，因為地固座標系本身在旋轉：

```
x' =  cos θ · x + sin θ · y
y' = −sin θ · x + cos θ · y
v_ecef = R(θ) · v_teme + (ω · y', −ω · x', 0)       ω = 7.2921158553e-5 rad/s
```

漏掉速度的修正項，位置仍然正確，但**距離變化率**（都卜勒）會錯——這是只看位置的測試抓不到的 bug，所以參考資料同時比對位置與速度。

### 第二步與第三步：站心座標

```csharp
// src/SkyPass.Core/Coordinates/ObserverSite.cs（節錄）
public LookAngles Observe(in EcefState sat)
{
    var rho = sat.PositionKm - EcefKm;                      // 觀測點指向衛星
    var s = _sinLat * _cosLon * rho.X + _sinLat * _sinLon * rho.Y - _cosLat * rho.Z;   // 南
    var e = -_sinLon * rho.X + _cosLon * rho.Y;                                         // 東
    var z = _cosLat * _cosLon * rho.X + _cosLat * _sinLon * rho.Y + _sinLat * rho.Z;    // 天頂
    var range = rho.Norm;
    var elRad = Math.Asin(z / range);
    var az = Angles.Normalize360Deg(Math.Atan2(e, -s) * Angles.RadToDeg);
    var rangeRate = rho.Dot(v) / range;
    // …
}
```

`ObserverSite` 在建構時就把 sin、cos 算好存起來；每次觀測不重算三角函數，也不配置記憶體。

### 一個「免費」的導數：仰角變化率

過境搜尋（4.5 節）需要知道仰角是在上升還是下降。可以用數值微分（多算一個時間點），但其實可以從已有的量直接推導：

```
仰角 El = asin(Z / ρ)，其中 Z = 天頂分量，ρ = 距離
dEl/dt = (Ż·ρ − Z·ρ̇) / (ρ² · cos El)
```

`Ż` 是速度在天頂方向的分量，`ρ̇` 就是距離變化率——兩者在同一次計算中都有了。**不需要額外的 SGP4 呼叫**。

## 4.5 過境搜尋：不漏的演算法（本章重點）

### 問題定義

給定一個函數 f(t) = 仰角(t) − 遮罩，在時間範圍 [t₀, t₁] 內找出所有「f ≥ 0 的連續區段」，並求出區段的起點（AOS）、終點（LOS）與 f 的最大值。

限制：

- 每次計算 f(t) 需要一次 SGP4 + 座標轉換（約 1 微秒），不能算每一個瞬間
- **不得漏掉任何最大值 ≥ 0.05° 的區段**
- 100 顆衛星 × 7 天要在 2 秒內算完

### 天真的做法，以及它為什麼會漏

每 Δ 秒取樣一次，看 f 有沒有變號：

```
f(t)
 │          ╭─╮   ← 掠過過境：最大值只比 0 高一點點
0├──●───────●─┼─●───────●────    ● = 取樣點
 │           ╰╯
 └──────────────────────────► t
       兩個取樣點都 < 0 → 天真做法認為「沒有過境」
```

一個最大仰角只比遮罩高 0.1° 的過境，在遮罩之上可能只停留十幾秒。只要取樣間隔比這長，就可能兩個取樣點都落在遮罩下方——**整個過境消失**。把 Δ 縮小可以降低機率，但永遠無法消除，而且會變慢。

### 關鍵想法：看導數的符號

如果 f 在兩個取樣點之間有一個**局部最大值**，那麼 f′ 在左端點 > 0（還在上升）、在右端點 < 0（已經下降）。

```
            f′ > 0    f′ < 0
              ↗ ╭─╮ ↘
0├──────────●─┼───┼─●────
 │         a  ╰───╯  b
            f(a) < 0, f(b) < 0，但 f′(a) > 0 > f′(b) → 中間一定有極大值！
```

演算法對每一個取樣區間 [a, b]：

1. **f 變號** → 有 AOS 或 LOS，用二分法求根到 1 毫秒
2. **f′ 由正轉負** → 區間內有極大值，用二分法求 f′ 的根，得到極大值的位置與數值
   - 若極大值 ≥ 0，即使兩端 f < 0，這也是一個過境：在 [a, 極大] 與 [極大, b] 各求一次根
3. 都沒有 → 區間內沒有事件

f′ 就是 4.4 節的仰角變化率，**每個取樣點都已經算好了**，所以偵測極值不需要任何額外成本。

```csharp
// src/SkyPass.Core/Passes/PassFinder.cs（節錄）
private void ProcessInterval(Sample a, Sample b)
{
    Sample? max = a.FDot > 0 && b.FDot <= 0 ? RefineMax(a, b) : null;

    if (_open is null)
    {
        if (b.F >= 0)
        {
            // AOS 在 (a, b]；若區間內有極大值，極大值必 ≥ f(b) ≥ 0，AOS 在 (a, max]
            var aos = RefineCrossing(a, max ?? b);
            _open = new OpenPass(aos, startedBeforeWindow: false);
            _open.Consider(max);
            _open.Consider(b);
        }
        else if (max is { F: >= 0 } m)
        {
            // 兩端都在遮罩下、中間短暫升起的掠過過境
            _open = new OpenPass(RefineCrossing(a, m), startedBeforeWindow: false);
            _open.Consider(m);
            Close(RefineCrossing(m, b), endsAfterWindow: false);
        }
        return;
    }

    _open.Consider(max);
    if (b.F < 0)
    {
        Close(RefineCrossing(max ?? a, b), endsAfterWindow: false);
    }
    else
    {
        _open.Consider(b);
    }
}
```

### 這個演算法什麼時候會漏？

它只在**一個取樣區間內同時出現一個極大值與一個極小值**時才可能漏判（此時 f′ 在兩端同號）。
對近地軌道，仰角的相鄰極大與極小值大約相隔半圈（約 45 分鐘），遠大於取樣間隔 30 秒。

這**不是數學證明**，而是一個基於物理的論證。因此我們用測試強力驗證它（第 6 章）：

- 與一個**完全不同**的暴力演算法（逐秒取樣）比對 320 組隨機情境
- 60 組刻意構造的掠過過境：先用暴力解找到一個過境的最大仰角 E，再把遮罩設成 E − δ（δ 在 0.05° 到 0.5° 之間），要求全部找到

> **教學重點**：當你無法證明一個演算法是對的，就要**把它的假設講清楚**（README 已知限制有寫），
> 並設計**專門攻擊那個假設**的測試。構造「剛好掠過」的案例，就是在攻擊「取樣會漏」這個弱點。

### 視窗拆分不變性：全域對齊的取樣格點

第 2 章的不變量要求：把 [t₀, t₂] 拆成 [t₀, t₁] 與 [t₁, t₂] 兩次預測，合併後要與一次預測相同。

如果取樣點是「從起點開始每 30 秒」，兩次預測的取樣點就不同，求根的結果會有微小差異，甚至可能一邊抓到某個極值、另一邊沒抓到。解法很簡單：

```
取樣時刻 = 1970-01-01 00:00 UTC 起每 30 秒的整數倍，再加上時間範圍的起點與終點
```

不管時間範圍怎麼切，**同一個時刻永遠用同一組取樣點**。不變量從「希望成立」變成「結構上成立」。

```csharp
var gridIndex = (long)Math.Floor(start.SecondsSince(GridAnchor) / SampleStepSeconds) + 1;
// …
var t = GridAnchor.AddSeconds(gridIndex * SampleStepSeconds);
```

### 邊界與失敗

| 情況 | 處理 |
|---|---|
| 起點時已在遮罩上 | AOS = 起點，標示「起點前已開始」；最大仰角取範圍內的最大值 |
| 終點時尚未落下 | LOS = 終點，標示「終點後才結束」 |
| SGP4 傳播失敗（衰減） | 在最後成功與第一次失敗之間二分到 0.5 秒，停止並產生診斷；若在過境中，以最後可傳播的時刻作為 LOS |

### 複雜度

設時間範圍長度 T、取樣間隔 Δ、過境數 P、求根容差 ε：

```
計算次數 ≈ T/Δ（取樣） + P × 3 × log₂(Δ/ε)（每個過境求 AOS、最大、LOS 三個根）
         = 604800/30 + 30 × 3 × log₂(30/0.001)
         ≈ 20160 + 30 × 3 × 15 ≈ 21500 次（每顆衛星、7 天）
```

100 顆衛星約 215 萬次，每次約 1 微秒，單執行緒約 2 秒，8 執行緒約 0.3 秒——與實測（單執行緒 2.6 秒、8 執行緒 0.32 秒）吻合。

## 4.6 陰影搜尋：同一招再用一次

衛星是否被太陽照到，用圓柱陰影模型判定：

```
若 r·ŝ < 0（在地球背對太陽的一側），且 |r − (r·ŝ)ŝ| < 地球半徑，則在陰影內
```

### 把「布林判斷」變成「連續函數」

求進出陰影的時刻需要求根，求根需要連續函數。定義「陰影邊界距離」：

```
m(t) = |r⊥| − Re   當 r·ŝ < 0（r⊥ = r − (r·ŝ)ŝ，垂直於太陽方向的分量）
     = |r|  − Re   當 r·ŝ ≥ 0
```

在 r·ŝ = 0 處兩式相等（因為此時 r⊥ = r），所以 m 連續；m < 0 就是在陰影內。

### 短陰影問題

當軌道面與太陽方向的夾角（β 角）接近臨界值時，衛星只會「擦過」地影邊緣，陰影可能只持續幾秒鐘——比 10 秒的取樣間隔還短。這和掠過過境是**同一個問題**，所以用同一個解法：

1. 以解析式計算 m 的變化率（視太陽方向為定值）：`dm/dt = r⊥·v⊥ / |r⊥|`
2. m 不變號但變化率由負轉正 → 區間內有極小值
3. 用**黃金分割搜尋**在 m 本身（而不是在變化率上）求極小值；若極小值 < 0，在兩側各求一次根

為什麼要在 m 本身求極值，而不是求變化率的根？因為變化率的公式把太陽方向視為不動，而太陽每天移動約 1°，
這讓變化率有微小偏差。用它來「偵測有沒有極值」已經足夠，但極值的位置要用精確的 m 來求。

這個改進是在**外部審查**後加入的（第 7 章）。測試以幾何方式構造了 0.97 到 8.39 秒的擦邊陰影，修改前會漏掉，修改後全部找到。

> **教學重點**：同一個演算法模式（取樣 + 導數偵測極值 + 求根）解決了兩個看似不同的問題。
> 學會辨認問題的**結構**，比記住個別問題的解法更重要。

## 4.7 可目視：兩個條件的交集

可目視 = 衛星受日照 **且** 觀測點太陽仰角 < −6°。兩個條件各自有自己的邊界時刻：

```
陰影：     ████████░░░░░░░░░░░░░░████████    （░ = 受日照）
太陽仰角：  ░░░░░░░░░░░░░████████████████    （█ = 天色夠暗）
可目視：             ░░░░░░░░░░              取兩者的交集
          AOS                        LOS
```

演算法：

1. 收集所有邊界時刻：陰影事件（4.6 節）、太陽仰角跨越 −6° 的時刻（取樣 + 二分）、AOS、LOS
2. 排序後，每個子區間取中點判斷兩個條件，合併相鄰的「可目視」子區間
3. 總長不足 1 秒不標示（需求規定）

這是「區間交集」問題的通用解法：**收集所有可能的邊界，然後逐段判斷**。不需要分析所有條件組合的情況。

## 4.8 都卜勒

```
接收頻率 = f₀ × (1 − ṙ / c)
```

其中 ṙ 是距離變化率（接近時為負，所以頻率升高），c = 299792.458 km/s。以 145.8 MHz、ṙ = −7 km/s 計算：

```
145.8e6 × (1 + 7/299792.458) = 145,803,404 Hz   →  頻移 +3404 Hz
```

公式本身很簡單，正確性完全取決於距離變化率——也就是取決於 4.4 節速度轉換的修正項有沒有寫對。

## 4.9 天空圖與 DPI：小地方的正確性

### 天空圖投影

天空圖是「仰望天空」的視角：天頂在圓心、地平線在外圈。**仰望時東西方向是左右相反的**——面向北方抬頭看，東邊在左手邊。

```
半徑 r = R × (90° − 仰角) / 90°
x = 中心x − r × sin(方位角)     ← 減號：東在左
y = 中心y − r × cos(方位角)     ← 減號：螢幕 y 向下，北在上
```

### DPI 縮放：不要累加取整後的數字

在 150% 縮放的螢幕上，時間軸 24 個小時刻度，每格 960/24 = 40 邏輯像素 → 60 實體像素，沒問題。
但如果每格是 960/7 ≈ 137.14 邏輯像素（縮放 130%）：

| 做法 | 第 7 格的位置 |
|---|---|
| 累加：`round(137.14 × 1.3) × 7 = 178 × 7` | 1246 |
| 各自計算：`round(7 × 137.14 × 1.3)` | **1248** |

累加取整會產生 2 像素的累積誤差，刻度與資料區段就對不齊了。規則是：**每個座標都從精確的邏輯座標各自乘上倍率再取整，永遠不要累加取整後的值**。

```csharp
// src/SkyPass.Core/Layout/Timeline.cs
public readonly record struct DpiScaler(double Scale)
{
    public int ToPixels(double logical) => (int)Math.Round(logical * Scale, MidpointRounding.AwayFromZero);
    public PixelSpan SnapSpan(double logicalStart, double logicalEnd) => new(ToPixels(logicalStart), ToPixels(logicalEnd));
}
```

這樣相鄰兩個區段共用同一條邊（前一段的 End 就是後一段的 Start），不會有縫隙或重疊。

## 4.10 本章小結

| 技巧 | 用在哪裡 | 可以帶走的原則 |
|---|---|---|
| 選擇表示法避開精度問題 | 兩段式儒略日 | 先估算誤差，再決定表示法 |
| 刻意不重構 | SGP4 移植 | 正確性來自一致性時，保持結構相同 |
| 把可變狀態變成區域變數 | SGP4 執行緒安全 | 不可變物件天生執行緒安全 |
| 取樣 + 導數偵測極值 + 求根 | 過境搜尋、陰影搜尋 | 只看函數值會漏；看導數就知道「中間有沒有東西」 |
| 全域對齊的取樣格點 | 視窗拆分不變性 | 讓不變量成為結構上的保證 |
| 收集邊界、逐段判斷 | 可目視區段 | 區間交集的通用解法 |
| 各自取整，不累加 | DPI 縮放 | 誤差不應該隨數量累積 |
