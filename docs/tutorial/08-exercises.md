## A.2 動手實驗（建議第一週完成）

這些實驗不需要寫新程式，目的是熟悉專案並親眼看到測試的作用。

1. **建置與執行**：`dotnet test` 全部通過；用範例資料啟動 App，找到一個「可目視」的過境，觀察天空圖上的黃色線段
2. **破壞實驗**：依序做下列修改，各自執行測試，記錄**哪些測試失敗、失敗訊息是否足以定位問題**，然後還原
   - 把 `TleParser.ComputeChecksum` 中「負號計 1」改成「負號計 0」
   - 把 `Frames.TemeToEcef` 中速度的 `+ EarthRotationRadPerSec * y` 刪掉
   - 把 `PassFinder.SampleStepSeconds` 改成 300
   - 把 `PassPredictor` 的結果排序刪掉
   - 把 `JulianDate.MinutesSince` 改成 `(Value - epoch.Value) * 1440.0`
3. **觀察參考資料**：開啟 `tests/SkyPass.Tests/TestData/sgp4_random.csv`，找出一筆錯誤碼不為 0 的資料，用 `Sgp4Propagator` 重現它

> **給教師**：破壞實驗的第 5 項很有代表性——一個數學上等價的改寫，實測讓 5 個測試失敗：
> 儒略日往返與單調性、單位換算、仰角變化率對數值微分、都卜勒頻移零點、即時追蹤逐秒參考。
> 但 **SGP4 參考測試與 GMST 測試全部通過**——因為它們直接以 tsince（分鐘數）或兩段式儒略日輸入，
> 根本不經過 `MinutesSince`。這是討論「預言的盲點」（第 6 章 6.1 節）的絕佳素材：
> 請學生解釋為什麼這些測試沒抓到，以及如果只有它們，這個退化會不會被發現。

## A.3 延伸專題

### 專題 A：深空軌道支援（SDP4）　★★★★

目前週期 ≥ 225 分鐘的衛星標示為「不支援」。在 `Sgp4Propagator` 加入 Vallado 參考實作的深空分支（`dscom`、`dpper`、`dsinit`、`dspace`）。

- **需求分析**：opsmode `'a'` 與 `'i'` 在深空分支中有差異，要用哪一個？
- **測試**：`SGP4-VER.TLE` 中有 20 組以上深空案例，可直接使用；擴充 `gen_sgp4.py` 產生隨機深空軌道
- **挑戰**：深空分支的 `dspace` 會**累積狀態**（數值積分），如何維持「傳播器不可變、執行緒安全」？
- **評量重點**：與參考實作的一致性、執行緒安全的設計

### 專題 B：天線轉台控制　★★★

加入「天線轉台」輸出：過境期間每秒輸出方位角與仰角指令（例如 Hamlib `rotctld` 協定的文字格式，先輸出到檔案或主控台即可）。

- **需求分析**：轉台通常不能轉超過 360°，過境經過正北時怎麼辦？（搜尋「flip mode」）
- **架構**：轉台控制屬於哪一層？如何在沒有實體轉台時測試？
- **評量重點**：分層是否正確、`TimeProvider` 的使用、邊界情況（正北、正上方）的處理

### 專題 C：大氣折射修正　★★

需求假設「不考慮大氣折射」。實際上低仰角的折射可達 0.5°，會讓衛星「提早出現」。

- 研究一個折射模型（例如 Bennett 公式），加入設定選項
- 分析：開啟折射後，哪些不變量仍然成立？過境搜尋需要改嗎？（提示：仰角變化率）
- 設計測試：折射修正後的 AOS 一定比較早嗎？

### 專題 D：半影與陰影模型　★★★

把圓柱陰影換成考慮太陽視直徑的錐形模型，區分本影、半影。

- 「受日照」變成 0 到 1 之間的連續值，可目視的定義要怎麼改？
- 陰影搜尋的邊界函數要怎麼定義才連續？

### 專題 E：以 iCalendar 匯出過境　★

把過境表匯出成 `.ics` 檔，讓社員匯入手機行事曆。

- 研究 RFC 5545；時區要怎麼處理？（Core 一律 UTC 的設計在這裡有什麼好處？）
- 寫出與 CSV 匯出同等級的測試（欄位、跨日、跳脫字元）

### 專題 F：重寫 UI 框架　★★★

用另一個 UI 框架（例如 Avalonia，**僅限練習**，原需求禁止）重寫 App 層。

- 量化驗證：Core、Data、Presenters 需要修改幾行？
- 比較 retained mode 與 immediate mode 下，「快照 + 每幀拉取」的模型是否仍然合適

## A.4 期末專題：用同樣的方法做一個新系統

選一個「有計算核心、有時間軸、有畫面」的題目，完整走過本教材的流程。例如：

| 題目 | 計算核心 | 對應本專案的哪個技巧 |
|---|---|---|
| 日出日落與月相預報 | 太陽、月球位置 | 事件搜尋（取樣 + 求根）、時區處理 |
| 公車到站預估 | 路線、速度模型 | 純函數核心、即時更新、快照 |
| 潮汐預報 | 調和分析 | 參考資料比對、精度估算 |
| 行星合相預報 | 行星星曆 | 極值搜尋（角距離的極小值） |

### 必須交付

1. 需求分析：利害關係人、使用情境、**量化的**非功能需求、驗收標準
2. 系統分析：詞彙表、領域模型、資料流、狀態圖、**不變量**、風險分析
3. 架構設計：分層與依賴圖、執行緒模型、至少 3 條 ADR
4. 實作：核心計算不依賴 UI；所有「現在時間」可注入
5. 測試：至少兩種不同的預言；至少 3 組性質或蛻變測試；一個獨立的參考演算法
6. 反思：至少 3 個「真實踩過的坑」，說明怎麼抓到、改了程式還是測試、為什麼

## A.5 評量建議

| 面向 | 比重 | 優秀 | 待加強 |
|---|---:|---|---|
| 需求分析 | 15% | 每條品質需求都量化；主動定義灰色地帶；提出的問題都會改變做法 | 只有功能清單；「要快」「要準」 |
| 系統分析 | 15% | 不變量清楚且直接變成測試；風險分析決定了驗證的重點 | 只有類別圖 |
| 架構設計 | 20% | 依賴方向正確；副作用可注入；ADR 說清楚代價 | 邏輯寫在 UI 事件處理器裡 |
| 演算法與實作 | 20% | 能說明正確性的論證與它的假設；有複雜度估算 | 「跑起來看起來對」 |
| 測試 | 20% | 多種預言、可重現的隨機測試、刻意構造的困難案例 | 只有幾個手寫案例 |
| 反思與溝通 | 10% | 坑的描述包含「怎麼抓到的」與「為什麼這樣修」 | 只列出改了什麼 |
